# 会议纪要输出模板（Markdown）

> 用途：作为 `summarize.py` 提示词中的输出骨架（已落到 `MINUTES_SKELETON` / `MINUTES_RULES` 两个常量）。模型只负责按骨架填充内容，**不得增删章节标题、不得改变层级**。
> 结构参考腾讯会议「元宝纪要」：概览 → 按议题分章 → 分条要点 → 结论与待办收尾。
>
> **改动本文件时，必须同步 `summarize.py` 里的 `MINUTES_SKELETON` / `MINUTES_RULES`**，两处是同一份约定的副本。

---

## 一、模板骨架

> 注意：**不含 `# 会议标题` 一行**。客户端纪要面板顶部已经渲染了会议标题，模型再输出一次会重复；将来做导出/复制时，由前端在渲染前拼上标题。

```markdown
## 会议概览

- **会议主题**：{一句话概括这场会在做什么，与标题同义时不要另起说法}
- **会议摘要**：{2~4 句。第一句说是场什么会，第二句说主要讨论/排查了什么，第三句说结论或当前状态}
- **主要发言人**：{仅当转写能区分说话人时才输出；否则整行删除}

## 一、{议题一}

### 1. {子议题}

- **{要点标签}**：{具体内容，带数字、结论或现象}
- **{要点标签}**：{具体内容}

### 2. {子议题}

- **{要点标签}**：{具体内容}

## 二、{议题二}

### 1. {子议题}

- **{要点标签}**：{具体内容}

## 决议事项

- **{决议要点}**：{已明确拍板的结论}

## 待办事项

- [ ] {动词开头的动作}
- [ ] {动词开头的动作}（负责人：{姓名}；时限：{时间}）

## 风险与遗留问题

- **{风险名}**：{会造成什么影响}
```

**章节可省略规则**：`决议事项` / `待办事项` / `风险与遗留问题` 三节中，**没有内容就整节删除**，绝不写「无」「暂无」或空占位。
**可选行规则**：`主要发言人`（当前 ASR 无说话人分离，默认不输出）、待办中的「负责人 / 时限」（转写里没提到就不写，禁止编造人名）。

## 二、填充规则（直接写进 system prompt）

### 结构与粒度

1. 只输出骨架里的章节，不得增删章节标题、不得改变层级；正文从「## 会议概览」开始，不要重复输出会议标题。
2. 议题章节 2~6 个，每个议题下子议题 1~4 个，每个子议题下要点 1~5 条。
3. 议题名用动宾短语（如「视频会议音频回音排查」），禁止「其他」「补充说明」这类空标题。
4. 每条要点写成「**标签**：内容」，标签 4~10 字，内容不超过 60 字，一条只说一件事。
5. 要点必须落到具体信息（数字、现象、结论、决定），禁止「进行了深入讨论」「大家积极发言」这类空话。
6. 按信息重要度排序，不按发言时间写流水账；同一议题内的要点合并去重。

### 事实约束

7. 只写转写里真实出现的内容；没提到或听不清的一律不写，宁可少一条，不许猜测补全。
8. 人名、数字、版本号、机型等照抄转写，不做「大概」「似乎」式推断。
9. 无法确认的归因不要落到某个人头上（如「某成员未戴耳机」），改写为现象描述（如「部分人员佩戴耳机后仍存在回音」）。

### 三节定性（去重的关键）

10. 决议事项：明确拍板的结论，有「确定 / 决定 / 就用这个方案 / 不再做 X」的语义；仅陈述现状的不算决议。
11. 待办事项：动词开头的可执行动作，一条只做一件事；只有转写里提到责任人或时限时才补括号。
12. 风险与遗留问题：本轮未解决、且尚无明确下一步动作的隐患，只写影响与不确定性。
13. 同一事实只能出现在决议 / 待办 / 风险中的一节，优先级：待办事项 > 决议事项 > 风险与遗留问题。判断方法：某个隐患一旦已经拆成具体动作，就只留在待办里，风险一节不得再写它。例：已列「排期 50 人并发测试」到待办，风险一节就不要再写「50 人规模未验证」。
14. 决议事项 / 待办事项 / 风险与遗留问题三节没有内容就整节删除，禁止写「无」「暂无」或留空占位。

### 排版

15. 全篇中文、使用全角标点；数字与英文术语保持原样（如 FunASR、50 人）。
16. 正文总长 600~1500 字，待办不超过 8 条。
17. 只输出 Markdown 正文，不要代码块围栏、不要额外前言或结尾寒暄。

## 三、填充示例（用 0910 那场测试会，含去重效果）

```markdown
## 会议概览

- **会议主题**：多人会议系统并发接入与投屏能力测试
- **会议摘要**：本次为多人会议系统测试，实际参与约 20 至 30 人，重点验证多参会人接入、游客登录（无痕浏览器）、摄像头开启、投屏与画面清晰度。测试中发现无痕浏览器第二个游客入口缺少进房凭证并跳转登录页、部分成员画面模糊卡顿、成员列表人数与实际不一致等问题。会议决定先结束本轮测试，后续聚焦投屏功能验证。

## 一、多参会人接入测试

### 1. 并发规模与画面表现

- **参与规模**：实际参与约 20 至 30 人，未达到近 50 人的并发预期。
- **性能表现**：多人开启摄像头或投屏时出现画面模糊与卡顿。

### 2. 成员列表与在线状态

- **人数不一致**：成员列表显示人数与实际参会人数、开启摄像头数不一致。
- **退出后残留**：成员退出后列表仍显示该成员，且部分成员在列表中不可见。

## 二、游客登录（无痕浏览器）测试

### 1. 进房凭证缺失

- **现象**：无痕浏览器中第二个游客进入时提示缺少进房凭证，跳转用户名/密码/验证码登录页，无法正常入会。

### 2. 缓存与登录态排查

- **待查方向**：判断浏览器缓存与认证信息是否导致游客登录状态异常，需整理截图并在群内同步。

## 三、投屏功能测试

### 1. 测试结论

- **验证优先级**：本轮测试优先验证投屏功能。
- **未完成项**：投屏清晰度、卡顿与带宽占用尚未完成观察。

## 决议事项

- **优先验证投屏**：本轮测试优先验证投屏功能。
- **游客登录测试方式**：改用无痕浏览器测试游客登录流程。
- **测试范围收敛**：本轮先用当前方式完成自用测试，不再并行测试多场会议同时进行。
- **本轮结束**：结束本轮多人会议测试。

## 待办事项

- [ ] 排查无痕浏览器第二个游客进入时缺少进房凭证、跳转登录页的问题
- [ ] 确认浏览器缓存与认证信息是否导致游客登录状态异常，整理截图发群
- [ ] 继续测试投屏功能，观察投屏清晰度、卡顿与带宽占用
- [ ] 补充近 50 人同时开启摄像头的并发与带宽验证
- [ ] 排查成员列表人数统计不一致、退出后仍显示、部分成员不可见的问题
- [ ] 评估卡顿或画面模糊时的降码率、降分辨率与踢人策略
```

> 注：本场 6 项风险**均已拆成上面的待办**，按第 13 条去重规则不再重复出现在风险一节，因此该章节整体省略。这正是原版纪要里「同一件事在待办和风险各写一遍」的修正效果。
>
> 如果希望风险章节始终存在，把第 12 条改成「风险写影响面，待办写动作，允许同一事项在两节各出现一次（措辞不得重复）」，并删掉第 13 条即可 —— 但会退回目前的观感。

## 四、落地实现（2026-09-10 已上线 test 环境）

### 1. 客户端 Markdown 渲染

- 新增 `client/src/utils/minutesMarkdown.ts`：`markdown-it` 渲染，配置 `html:false`（禁用内联 HTML，正文里的 `<script>` 等会被转义）、`breaks:true`（兼容历史纯文本纪要的换行）。
- markdown-it 核心不含 GFM 待办语法，渲染后把 `<li>[ ] 动作` 替换成 `.md-task` + `.md-task-box` 方框。
- `LobbyView.vue` 正文改为 `.detail-minutes-md` + `v-html="minutesHtml"`；样式在文件底部全局 `<style>` 块（该块非 scoped，**不能用 `:deep()`**）。
- 旧的 `structured.todos/decisions/risks` 三个前缀列表**保留未删**：历史数据仍有值，会照常渲染；新数据三组数组为空，自然不显示。

### 2. `summary` 与 `structured` 的关系（采用方案 B）

- `summary` 存完整 Markdown（含决议/待办/风险章节）；`structured` 的三组数组新数据一律为空，仅为兼容历史数据与前端旧渲染保留。
- 回调结构未变（`summary` / `structured` / `model`），**后端 Go 代码零改动**。

### 3. 模型调用方式

- **不能用 `llm.with_structured_output()`**：DeepSeek 该模型对 `response_format` 返回 `400 This response_format type is unavailable now`，会一直异常。
- 也不能用 `("system", SYSTEM_PROMPT)` 模板：骨架里的 `{会议主题}` 等占位符会被 `ChatPromptTemplate` 当成待填变量，抛 `INVALID_PROMPT_INPUT`。
- 最终实现：`SystemMessage(content=SYSTEM_PROMPT)`（字面量）+ `HumanMessage` 直接 `llm.invoke()`，再 `_strip_code_fence()` 容错模型偶发的 ``` 围栏或 JSON 包裹。

### 4. 待办：转写原文入口

腾讯元宝纪要支持展开原始记录。当前 `transcript` 已入库（`mediumtext`）但前端未展示。若要加，建议做成纪要面板里的折叠区块，和模板解耦，单独排期。
